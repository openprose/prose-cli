# Service operation corpus

Shared black-box cases for `prose cli` service operations
(see [`cli/SPEC.md`](../../../SPEC.md)). Rust and Bun
implement them independently; neither product's unit tests may redefine them.

One directory per feature. The directory name is the `feature` of the
operations in [`operations.v1.json`](../../../shared/service/operations.v1.json):

| Directory | Operations |
| --- | --- |
| `framework/` | parsing, confirmation, `--preview`, error classification, per-cause invocation Actions and `suggestedArgv` (`error-action-*`), transport limits, client identity, `service operations`, `service capabilities`, `service guide` (the `service-guide-*` and `help-service-guide-topic` cases are generated by `cli/ci/render_service_help.py --write`; cases here may name any operation) |
| `discovery/` | `service status`, `service triage`, `model list`, `example list/show`, `repo list` |
| `runs/` | `run quote/submit/watch/input/cancel` |
| `run-records/` | `run list/show/download/share` |
| `programs/` | `program list/show/save/visibility/delete/revisions/draft` |
| `results/` | `result list/show/publish/unpublish` |
| `jobs/` | `job ...` |
| `wallet/` | `wallet balance/events/usage/redeem/topup` |
| `organizations/` | `org ...` (organization operations, plus `org list` human bytes, trailing options and credential teaching; its JSON contract is covered by the account and registry cases) |
| `account/` | `auth status/login/logout` and `package ...`: credential teaching and trailing global options |

Every case targets the production service: a fixture's `environment`, when
present, is `production`, its `credentials` hold only the stored production key,
and no argv selects a service. The CLI has no other service origin to select.

## Case files

Each case is one file, `<id>.json`, matching `$defs/case` in
[`service-fixture.schema.json`](../../runner/service-fixture.schema.json):

```json
{
  "id": "wallet-balance-json",
  "feature": "wallet",
  "operation": "wallet.balance",
  "description": "Balance projection drops customer_id and nanos fields.",
  "argv": ["--output", "json", "cli", "wallet", "balance"],
  "fixture": {
    "environment": "production",
    "credentials": {"production": "rr_test_11111111111111111111111111111111"},
    "storeAvailable": true,
    "exchanges": [{"method": "GET", "path": "/wallet/balance",
                   "requestHeaders": {"Authorization": {"present": true}},
                   "status": 200, "body": {"customer_id": "cus_example", "balance": {"...": "..."}}}]
  },
  "exitCode": 0,
  "stdout": {"json": {"schema": "openprose.service-operation/1", "...": "..."}}
}
```

Rules enforced by `service_operations.py --validate`:

- the file name is the case id, and `feature` matches the directory;
- every exchange is a request declared by the case's operation (method and path
  template; query keys must be declared), except in `framework/`;
- raw text bodies use `bodyText` or `expectedBodyText`; a string `body` is a
  registry-corpus convention and is refused here;
- expected envelopes validate against `service-operation.schema.json` and the
  operation's result schema; JSONL output of a stream operation validates
  against `service-event.schema.json` and ends with exactly one terminal line;
  JSONL output of a list operation (manifest `output.records`) is one
  `service-record.schema.json` line per item and one `service-page.schema.json`
  trailer whose `count` matches, and `meta` plus the records must satisfy the
  result schema; any other JSONL golden is the one envelope;
- a problem's exit code equals its taxonomy exit code;
- account report documents (`service-account`, `organization-list`,
  `package-operation`, a bare `runner-error`) validate against their schemas.

When a case runs, stdout must equal the expected document exactly. Fixtures fix
the clock (`clock`) and every minted UUID (`ids`), so nothing is normalized.
Structured modes must leave stderr empty unless the case declares `stderr`.
Fixture credentials and every `forbid` string must never appear in output.
After its own checks, every case whose JSON output carries
`problem.details.suggestedArgv` reruns that argv in the same fixture and
working directory, with `details.suggestedStdin` (or a stand-in secret when it
reads `-`) on standard input; an `INVOCATION_INVALID` exit 2 fails the case. `--round-trip-only` runs only that check.

## Commands

```sh
python3 cli/conformance/runner/service_operations.py --validate
python3 cli/conformance/runner/service_operations.py --feature wallet -- cli/rust/target/debug/prose
python3 cli/conformance/runner/service_operations.py --all -- cli/bun/dist/prose-test
```

`--all` also runs the determinism probe: every case of a paged operation
(manifest `output.paged`) runs twice on its fixture and must print the same
bytes, every JSON line canonical, and every `--output jsonl` case must end
with one terminal record whose `exitCode` is the process exit. It also runs
the manifest identity probe (`--output json cli service
operations` must print one envelope line whose result is the published manifest) and the examples probe:
every manifest example is run with an empty fixture and must not be rejected
by the grammar parser. A case's `stdout` may be `{"manifestBytes": true}` or
`{"manifestOperations": true}` (one canonical line per manifest operation). Only test-seam builds read
`PROSE_TEST_SERVICE_FIXTURE`; ordinary builds ignore it.

Cases are written by an oracle author who is not a builder of that feature,
from the frozen schemas, before implementation (see `protocol/OWNERSHIP.md`).
